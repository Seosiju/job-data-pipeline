# 데이터 파이프라인 및 서비스 확장 마스터 플랜

> 작성일: 2026-03-13
> 목적: 이 레포를 "크롤러 스크립트"에서 "운영되는 데이터 파이프라인 + 분석 서비스"로 확장하기 위한 기준 문서
> 성격: 중장기 기획서
> 상태: Active plan

## 1. 이 문서의 역할

이 문서는 앞으로의 구현 순서, 기술 선택 기준, 주의사항을 정리한 **상위 기획서**입니다.

- 현재 코드의 실제 동작은 `README.md`, `docs/architecture/system_architecture.md`, 실제 소스코드를 우선합니다.
- 앞으로 무엇을 만들지에 대한 방향과 우선순위는 이 문서를 우선합니다.
- 과거 `docs/reports/` 문서는 historical snapshot이며, 미래 작업 기준점으로 직접 사용하지 않습니다.

이 문서를 보고 이후 작업을 진행할 때 반드시 확인해야 할 질문은 세 가지입니다.

1. 지금 하려는 작업이 이 로드맵의 어느 단계에 속하는가
2. 지금 추가하려는 구조가 현재 단계에 비해 과한가
3. 이 변경이 "일일 파이프라인 운영"과 "분석 서비스화" 중 어느 목표를 직접 전진시키는가

## 2. 최종 목표

이 프로젝트의 최종 목표는 다음 3가지를 동시에 만족하는 것입니다.

### A. 데이터 파이프라인 운영 경험

- 매일 자동 실행되는 배치 파이프라인
- 수집 성공/실패, 데이터 신선도, 이력 추적
- 스키마 확장, 데이터 품질 관리, 운영 로그 관리

### B. 개인용 채용시장 분석 도구

- 내가 지원하려는 직무의 공고 흐름 파악
- 회사별 채용 빈도, 스킬 수요, 급여/요건 변화 확인
- 내 관심 키워드 기준 신규 공고 탐지

### C. 서비스 개발 경험

- 데이터를 제공하는 백엔드 API
- 데이터를 시각화하는 프론트엔드 대시보드
- 점진적으로 제품 형태를 갖춘 내부 서비스

## 3. 현재 상태 요약

현재 레포는 이미 아래를 갖추고 있습니다.

- Phase 1/Phase 2 오케스트레이션 코드 경로
- PostgreSQL 저장
- 다중 키워드 실행
- 증분 크롤링
- 공고 lifecycle 추적
- 공고 변경 이력 저장
- 테스트 가능한 코드 구조

다만 현재는 ingestion layer가 "완료"된 상태가 아니라, **정확성 안정화의 후속 보강이 남아 있는 상태**입니다.

현재 가장 먼저 해결해야 할 사실 기반 이슈:

1. Phase 1 정확성 감사와 Phase 2 메인 회사 페이지 전환은 완료됐지만, 회귀 검증 범위가 아직 fixture 중심으로 좁음
2. `company_page_url`를 DB에 저장하지 않아 Phase 2가 매 실행마다 JD를 다시 열어야 함
3. 수동 분석 스크립트가 새 Phase 2 흐름을 완전히 반영하지 못함

즉, 지금은 자동화와 서비스 확장 전에 **정확성 안정화의 마지막 10~20%를 마무리하는 단계**입니다.

앞으로 필요한 것은 다음 5개입니다.

1. 수집 정확성 안정화
2. 자동 실행
3. 운영 관측
4. 분석 가능한 데이터 모델
5. API + UI

## 4. 핵심 원칙

### 원칙 1. 가장 단순한 설계를 우선한다

- 지금 단계에서는 Airflow, Kafka, Redis, Celery, Kubernetes 같은 구조를 도입하지 않습니다.
- 단일 배치, 단일 DB, 단일 서비스 구조로도 충분히 목표를 달성할 수 있습니다.
- 먼저 작동하고, 관측 가능하고, 유지 가능한 구조를 만든 뒤 확장합니다.

### 원칙 2. 배치와 서비스는 분리하되 데이터는 공유한다

- 배치 파이프라인은 수집과 적재에 집중합니다.
- 서비스는 분석 결과 제공과 시각화에 집중합니다.
- 둘은 PostgreSQL을 통해 연결됩니다.

### 원칙 3. 원본 데이터를 먼저 보존하고, 정규화는 그 다음에 한다

- 스킬, 자격요건, 우대사항 같은 데이터는 처음부터 완벽히 정규화하려 하지 않습니다.
- 먼저 텍스트 원문을 저장합니다.
- 그 다음 규칙 기반 추출을 거쳐 정규화 테이블로 확장합니다.

### 원칙 4. 내부용 MVP를 먼저 만든다

- 첫 대상 사용자는 "나 자신"입니다.
- 처음부터 인증, 멀티유저, 권한관리, 퍼블릭 서비스 운영을 붙이지 않습니다.
- 먼저 내부용으로 유용한지 확인한 뒤 서비스화를 진행합니다.

### 원칙 5. 읽기 전용 API부터 시작한다

- 초기 서비스는 데이터 조회와 시각화만 담당합니다.
- 공고 수정/삭제/사용자 입력 중심 기능은 초기에 넣지 않습니다.

## 5. 목표 구조

권장 최종 구조는 아래와 같습니다.

```text
Scheduler
  -> Batch Runner
     -> JobKorea Crawl
     -> Validation / Upsert / History
     -> PostgreSQL

PostgreSQL
  -> operational tables
  -> analytics views / materialized views

Backend API
  -> read-only endpoints
  -> summary / jobs / companies / skills / trends

Frontend Dashboard
  -> overview
  -> new jobs
  -> skill demand
  -> company activity
  -> my target roles
```

### 권장 기술 선택

- Scheduler: `launchd` 또는 `cron/systemd`
- Batch: 현재 Python 배치 유지
- Database: PostgreSQL 유지
- Backend: FastAPI 권장
- Frontend: Next.js 권장
- Charting: Recharts 또는 ECharts 계열

## 6. 단계별 로드맵

### Phase 0. 수집 정확성 안정화

### 목표

- 검색 결과 파서와 회사 보강 경로가 실제 페이지 구조에 맞게 동작하는지 확정한다.
- 이후 자동 실행과 운영 지표가 잘못된 데이터를 확대 재생산하지 않게 만든다.

### 현재 상태

- Phase 1 검색 결과 파서 정확성 감사 완료
- Phase 2 `JD 상세 -> 회사 페이지 링크 -> 회사 페이지` 메인 경로 구현 완료
- 남은 일은 Phase 2 후속 보강과 회귀 범위 확장이다.

### 해야 할 일

- `company_page_url` 저장 구조 도입 여부 결정
- `scripts/analyze_detail_page.py`를 새 Phase 2 흐름에 맞게 정리
- JD 상세 / 회사 페이지 fixture 추가 확보
- selector fallback과 페이지 타입 판별 회귀 범위 확장
- 소규모 live run으로 Phase 1/2 end-to-end 확인

### 완료 기준

- 검색 결과 fixture 기준 메인 목록 카드만 안정적으로 반환
- 전역 `CardJob` 과수집 문제가 테스트로 재발하지 않음
- Phase 2가 JD URL 직접 파싱이 아니라 회사 페이지 기준으로 보강 경로를 가짐
- Phase 2 후속 보강 항목까지 반영되어 live run에서도 경로가 안정적으로 동작함

### Phase 1. 배치 자동화와 운영 안정화

### 목표

- 내가 직접 실행하지 않아도 매일 1회 실행되게 만든다.
- 실행 성공/실패와 수집량을 빠르게 확인할 수 있게 만든다.

### 해야 할 일

- OS 스케줄러 실제 등록
- `scripts/run_crawler.sh` 기준 자동 실행 경로 확정
- 실행 결과를 요약하는 최소 운영 뷰 또는 CLI 추가
- 실패 시 원인 파악 가능한 로그 경로 고정
- 최근 N회 실행 상태를 보여주는 운영용 조회 기능 추가

### 완료 기준

- 최소 3일 이상 수동 개입 없이 실행 가능
- 마지막 성공 시각과 실행 결과를 DB 또는 로그에서 바로 확인 가능
- 실패 시 로그 파일과 `crawl_runs`로 원인 역추적 가능

### Phase 2. 분석 가능한 데이터 모델 확장

### 목표

- "공고 수집"을 넘어 "직무 분석"이 가능하도록 데이터를 준비한다.

### 왜 필요한가

지금 스키마만으로는 공고 개수, 회사 수, 상태 정도는 볼 수 있지만,
"어떤 스킬이 많이 나오나", "내가 준비해야 할 역량은 뭔가", "공고 요구사항이 어떻게 바뀌나"까지 보기는 어렵습니다.

### 우선 추가할 데이터

`job_postings` 또는 연관 구조에 아래를 확장합니다.

- `description_text`
- `requirements_text`
- `preferred_qualifications_text`
- `employment_type`
- `education`
- `detail_crawled_at`

### 새로 고려할 테이블

#### `skills`

- 정규화된 스킬 사전
- 예: Python, SQL, Tableau, Airflow

#### `job_posting_skills`

- 공고와 스킬의 N:M 연결
- 원본 텍스트, 정규화 결과, 추출 시각 저장

#### `tracked_roles` 또는 유사 설정 구조

- 내가 추적하고 싶은 직무/키워드 목록
- 처음에는 DB 테이블보다 단순 설정 파일로 시작해도 됨

### 완료 기준

- 스킬/요구사항 분석을 위한 텍스트 필드가 저장됨
- 규칙 기반 스킬 추출 실험이 가능함
- 분석용 SQL 뷰를 만들 수 있을 정도로 데이터가 쌓임

### Phase 3. 분석 레이어 구축

### 목표

- 운영 DB를 바로 읽는 수준을 넘어서, 반복적으로 보는 지표를 안정적으로 제공한다.

### 권장 산출물

- `vw_daily_keyword_stats`
- `vw_active_jobs_by_keyword`
- `vw_company_hiring_activity`
- `vw_skill_demand`
- 필요 시 materialized view

### 우선 보고 싶은 지표

- 날짜별 신규 공고 수
- 키워드별 active/stale 공고 수
- 회사별 채용 활동량
- 스킬 등장 빈도
- 최근 7일 / 30일 변화량

### 완료 기준

- 분석 SQL이 ad-hoc query가 아니라 재사용 가능한 뷰로 정리됨
- 대시보드가 직접 복잡한 집계를 수행하지 않아도 됨

### 빠른 시각화 옵션

정식 API/프론트엔드 전에 내부 확인용으로 아래 중 하나를 잠깐 붙일 수 있습니다.

- Metabase
- Streamlit

단, 이들은 **임시 내부 시각화 도구**로만 사용합니다.
최종 제품 구조는 여전히 `FastAPI -> Frontend Dashboard`를 기준으로 합니다.

### Phase 4. 백엔드 API 구축

### 목표

- 프론트엔드가 DB에 직접 붙지 않게 하고, 서비스 레이어를 만든다.

### 권장 방식

- FastAPI 기반 read-only API
- `/health`
- `/summary`
- `/jobs`
- `/companies`
- `/skills`
- `/trends`
- `/tracked-roles`

### 설계 원칙

- 초기는 읽기 전용
- 페이지네이션 필수
- 정렬/필터는 명시적으로 제한
- DB 모델을 그대로 노출하지 말고 응답 스키마를 분리

### 완료 기준

- 프론트엔드가 API만으로 주요 대시보드를 구성 가능
- 핵심 분석 지표를 API로 제공 가능

### Phase 5. 프론트엔드 대시보드 구축

### 목표

### 우선 페이지

#### 1. Overview

### Phase 6. 서비스 고도화

### 이 단계에서만 고려할 것

- 메시지 브로커 도입
- 분산 크롤링

## 7. 가장 먼저 해야 할 실제 구현 순서

앞으로 바로 이어질 구현 순서는 아래가 가장 좋습니다.

### 1순위. 수집 정확성 안정화

- 이유: 잘못 수집하는 파이프라인을 먼저 자동화하면 운영 효율보다 데이터 오염이 더 커진다.

### 2순위. 자동 실행 실제 적용

- 이유: 정확성이 확보된 뒤에야 "계속 돌아야 하는 파이프라인"이 된다.

### 3순위. 운영 상태 확인용 최소 화면 또는 API

- 이유: 자동 실행만 되고 관측이 안 되면 운영 경험이 쌓이지 않음

### 4순위. 상세 텍스트 저장

- 이유: 이후 분석과 서비스 가치가 여기서 갈림

### 5순위. 스킬 추출 + 분석 뷰

- 이유: 사용자의 실제 취업 준비 가치가 여기서 생김

### 6순위. FastAPI

- 이유: 프론트엔드와 데이터 계층을 분리하기 위한 첫 단계

### 7순위. 프론트엔드 대시보드

- 이유: API와 분석 데이터가 갖춰진 뒤 만드는 편이 훨씬 단순함

## 8. 중요한 주의사항

### A. 기술 선택 관련 주의사항

### 1. Airflow/Dagster는 지금 넣지 않는다

현재는

- 단일 소스
- 단일 배치
- 일 1회 실행
- 복잡한 DAG 없음

상태이므로 OS 스케줄러로 충분합니다.

Airflow나 Dagster는 다음 조건이 생길 때만 검토합니다.

- 데이터 소스가 여러 개로 늘어남
- 일일 배치 외에 다단계 의존성이 생김
- 재시도/백필/스케줄 정책이 훨씬 복잡해짐

### 2. 메시지 브로커를 넣지 않는다

Kafka, RabbitMQ, Redis Queue는 현재 과합니다.

### 3. 프론트엔드가 DB에 직접 붙지 않게 한다

초기 내부 도구라도 API 레이어를 두는 것이 장기적으로 맞습니다.

### B. 데이터 설계 관련 주의사항

### 1. 원문 텍스트를 먼저 저장한다

처음부터 스킬만 추출해서 저장하면 나중에 규칙을 바꾸거나 재분석하기 어렵습니다.

반드시:

- 원문 저장
- 정규화 저장

순서를 지킵니다.

### 2. 기존 데이터를 조용히 덮어쓰지 않는다

- lifecycle 필드
- 변경 이력
- 원문 텍스트

이 세 가지는 추후 분석의 핵심입니다.

### 3. 마이그레이션은 가산적(additive)으로 한다

- 컬럼 추가
- 신규 테이블 추가
- 백필

순으로 가고, 기존 컬럼 삭제/의미 변경은 마지막까지 미룹니다.

### C. 운영 관련 주의사항

### 1. 파이프라인은 반드시 idempotent해야 한다

같은 날 다시 실행해도 데이터가 망가지지 않아야 합니다.

### 2. 로그와 지표를 분리한다

- 로그: 원인 추적
- DB 뷰/요약: 운영 지표

로그 파일만으로 운영 상태를 판단하지 않습니다.

### 3. 실패를 숨기지 않는다

- 배치 실패는 `crawl_runs`에서 보이게 해야 함
- 종료 코드는 유지해야 함
- 스케줄러 환경에서도 실패 여부를 알 수 있어야 함

### D. 제품화 관련 주의사항

### 1. 인증은 나중에

처음부터 로그인/회원 기능을 만들면 제품 개발이 아니라 인증 시스템 개발이 됩니다.

### 2. "내가 쓰는 도구"를 먼저 완성한다

초기 사용자 가치는 아래 질문에 답할 수 있어야 합니다.

- 오늘 새로 올라온 공고는 무엇인가
- 내가 보는 키워드는 최근 늘고 있는가 줄고 있는가
- 어떤 스킬이 많이 요구되는가
- 어떤 회사가 채용을 자주 하는가

### 3. 분석 가치 없는 UI부터 만들지 않는다

예쁜 화면보다 먼저 필요한 것은

- 정확한 지표
- 반복해서 확인할 가치가 있는 정보

입니다.

### E. 크롤링 관련 주의사항

### 1. 공격적으로 수집하지 않는다

- 일 1회
- 랜덤 딜레이 유지
- 과도한 병렬화 금지

### 2. 셀렉터 변경을 항상 염두에 둔다

대시보드 이전에 수집이 먼저 깨질 수 있습니다.

따라서:

- 수집 실패 탐지
- HTML 구조 변경 대응

이 필수입니다.

## 9. 단계별 완료 판단 기준

### Phase 0 완료로 볼 조건

- 검색 결과 fixture 기준 메인 목록 카드 수와 핵심 필드 추출이 테스트로 고정됨
- Phase 1 과수집 리스크가 해소됨
- Phase 2 회사 페이지 전환 경로가 구현 또는 최소한 검증 가능한 상태가 됨

### Phase 1 완료로 볼 조건

- 스케줄러 등록 완료
- 3일 이상 자동 실행 확인
- 최근 실행 상태를 보는 최소 운영 화면 또는 조회 기능 확보

### Phase 2 완료로 볼 조건

- 공고 원문/요구사항 텍스트 저장
- 스킬 추출 실험 가능

### Phase 3 완료로 볼 조건

- 핵심 분석 뷰 또는 materialized view 확보
- "지원 전략에 도움 되는" 지표 3개 이상 산출 가능

### Phase 4 완료로 볼 조건

- 프론트엔드가 API만으로 주요 데이터를 받음
- read-only API 문서화 완료

### Phase 5 완료로 볼 조건

- 내가 매일 실제로 사용하는 대시보드가 됨
- 신규 공고, 추이, 스킬 수요, 회사 활동이 한 화면 체계 안에 들어감
