> 상태: Historical snapshot
> 주의: 이 문서는 "정확한 실행 통계 / 증분 크롤링 / 상태-이력 / 운영성 정리"를 실제 구현하기 직전의 실행 계획을 기반으로 합니다.
> 현재 기준 판단은 `docs/status/current_status.md`, `docs/architecture/system_architecture.md`, `docs/plans/data_pipeline_service_roadmap.md`를 우선합니다.

## 0. 현재 관점에서 보면

이 문서에 적힌 큰 작업 스트림 중 아래 항목은 이미 반영되었습니다.

- 정확한 실행 통계 분리
- 증분 크롤링 도입
- 공고 lifecycle 필드 추가
- 공고 변경 이력 저장
- 수동 스크립트 `scripts/` 이동
- 로그/출력 1차 정리

따라서 이 문서는 현재 active plan이 아니라, 해당 배치가 어떤 문제를 해결하려고 했는지 이해하는 historical reference로 보는 편이 맞습니다.

## 1. 배경

현재 레포는 다음 상태까지 구현되어 있습니다.

- 목록/상세 2단계 크롤링 동작
- `companies`, `job_postings`, `crawl_runs` 저장 구조 확보
- 다중 키워드 실행 지원
- HTML 파싱 리팩토링 완료
- 저장 전 데이터 검증 로직 추가
- 테스트 기준 `75 passed, 15 skipped`

작성 당시 기준으로는 실제 운영과 데이터 신뢰성 측면에서 다음 문제가 남아 있었습니다.

- DB 중복 방지는 되지만 실행 통계가 실제 삽입 건수와 어긋날 수 있음
- Phase 2 대상 회사 조회가 동일 회사를 여러 번 반환할 수 있음
- 증분 크롤링이 없어 매번 앞 페이지부터 전부 순회함
- 공고 변경 이력과 활성/비활성 상태 추적이 없음
- 수동 점검 스크립트가 자동 테스트 경로와 가까워 역할이 혼동됨

이 단계의 목표는 “작동하는 크롤러”에서 멈추지 않고, **신뢰 가능한 일일 수집 파이프라인**으로 전환하는 것입니다.

## 2. 목표

### 핵심 목표

1. 실행 결과 수치가 실제 DB 반영 결과와 일치하도록 만든다.
2. 중복 수집 비용을 줄이는 증분 크롤링을 도입한다.
3. 공고 상태와 주요 변경 이력을 추적할 수 있는 최소 구조를 마련한다.
4. 운영자가 로그와 스크립트 구조를 보고 현재 상태를 바로 이해할 수 있게 만든다.

### 성공 기준

- Phase 1 결과가 `inserted / skipped / failed`로 분리 집계된다.
- 동일 회사가 Phase 2 대상에서 중복 처리되지 않는다.
- 이미 수집한 공고가 일정 수 이상 연속으로 나오면 목록 크롤링을 조기 종료한다.
- 공고의 `status`, `first_seen_at`, `last_seen_at`가 기록된다.
- 주요 필드 변경 시 이력 테이블에 기록된다.
- 운영용 로그와 수동 점검 스크립트 위치가 명확해진다.
- 관련 테스트가 추가되고 기존 테스트가 유지된다.

## 3. 범위

### 포함 범위

#### A. 데이터 신뢰성 강화

- `insert_job_posting()`가 실제 삽입 여부를 반환하도록 수정
- `main.py`에서 `inserted / skipped / failed`를 구분 집계
- `crawl_runs.jobs_collected` 의미를 “실제 신규 반영 건수” 기준으로 정리
- Phase 2 대상 조회 시 회사별 대표 `detail_url` 하나만 선택

#### B. 증분 크롤링 도입

- `detail_url` 기준 중복 존재 여부 조회 함수 추가
- 연속 중복 임계치 도달 시 목록 페이지 조기 종료
- 임계치는 환경변수 또는 설정값으로 관리
- 키워드별 조기 종료 여부를 로그에 남김

#### C. 상태/이력 추적

- `job_postings`에 상태 추적 필드 추가
- 일일 실행 시 `first_seen_at`, `last_seen_at` 갱신
- 마감/비노출 여부를 반영할 수 있는 최소 `status` 설계
- `deadline`, `salary`, `title` 등 주요 필드 변경 이력 저장 테이블 추가

#### D. 운영성 정리

- `print()`와 `logging` 역할 재정리 완료
- 수동 점검 스크립트 `scripts/` 이동 완료
- 불필요한 의존성(`pandas`) 유지 여부 재검토
- 운영 문서와 실행 경로를 다시 동기화

### 제외 범위

- 대시보드/시각화 UI
- Slack/이메일 알림
- 분산 크롤링
- Docker/Kubernetes 배포
- 클라우드 인프라 이전
- 분석용 SQL 리포트 작성

## 4. 작업 스트림

### 스트림 1. 데이터 신뢰성

#### 문제

- 현재는 `ON CONFLICT DO NOTHING`으로 중복을 막지만, 호출 측에서 실제 삽입 여부를 모르기 때문에 저장 통계가 부정확할 수 있음.
- 회사 상세 크롤링 대상도 회사 기준이 아니라 `(company, detail_url)` 기준에 가까워 중복 방문 가능성이 있음.

#### 구현 방향

- `database.py`
  - `insert_job_posting()`에서 실제 삽입 성공 여부 반환
  - `get_companies_without_details()`를 회사당 1건 반환하도록 재작성
- `main.py`
  - `total_saved` 대신 `inserted / skipped / failed` 분리
  - 콘솔 요약과 `crawl_runs` 기록 기준 일치

#### 산출물

- 정확한 실행 요약
- 키워드별 신규 수집 건수 신뢰성 확보
- 불필요한 상세 페이지 재방문 감소

### 스트림 2. 증분 크롤링

#### 문제

- 현재는 항상 1페이지부터 `MAX_PAGES`까지 순회함.
- 이미 충분히 수집된 키워드에서도 동일한 앞 페이지 비용을 계속 지불함.

#### 구현 방향

- `DatabaseManager.exists_job_posting(detail_url)` 추가
- 페이지별 파싱 후 연속 중복 카운트 누적
- 예: `CONSECUTIVE_DUPLICATE_THRESHOLD=20`
- 임계치 도달 시 해당 키워드 목록 수집 종료
- 조기 종료 시 로그와 요약 출력

#### 산출물

- 일일 수집 시간 단축
- 사이트 부하 감소
- 운영 비용 감소

### 스트림 3. 상태/이력 추적

#### 문제

- 현재 스키마는 “처음 본 공고를 저장”하는 데는 충분하지만, “언제까지 보였는지”, “무엇이 바뀌었는지”를 설명하지 못함.

#### 제안 스키마

`job_postings`에 다음 필드 추가:

- `status` (`active`, `stale`, `closed` 중 최소 1안 확정)
- `first_seen_at`
- `last_seen_at`
- 필요 시 `last_checked_at`

신규 테이블:

- `job_posting_history`
  - `job_posting_id`
  - `field_name`
  - `old_value`
  - `new_value`
  - `changed_at`

#### 구현 방향

- 동일 `detail_url` 재발견 시 `last_seen_at` 갱신
- 주요 필드 값이 변경되면 이력 저장
- 일정 기간 보이지 않은 공고를 `stale` 또는 `closed`로 전환하는 최소 규칙 수립

#### 산출물

- “신규 공고 수”와 “변경 공고 수” 구분 가능
- 향후 분석 기능의 기반 확보

### 스트림 4. 운영성 정리

#### 문제

- 운영 로그와 사용자 출력은 1차 분리됐지만 문서 마감이 더 필요함
- 수동 도구 경로는 정리됐지만 처음 보는 사람 기준 설명 보강 여지가 있음
- 현재 구조를 처음 보는 사람이 테스트/운영 스크립트를 혼동할 수 있음

#### 구현 방향

- 사용자 진행 표시와 디버그 로그 분리 상태 유지
- 수동 점검 스크립트와 자동 테스트의 경계 유지
- 문서와 스크립트 경로 재정리
- 의존성 재검토 후 필요 없는 패키지는 제거

#### 산출물

- 운영 로그 품질 향상
- 온보딩 비용 감소
- 테스트 체계와 도구 체계 분리

## 5. 권장 구현 순서

### 1단계. 데이터 신뢰성 먼저

- 실제 삽입 여부 반환
- 회사 상세 대상 중복 제거
- 실행 통계 수정

이 단계가 먼저인 이유:
- 이후 증분 크롤링과 이력 추적이 모두 “정확한 기준 데이터”를 전제로 하기 때문

### 2단계. 증분 크롤링

- 중복 존재 체크
- 연속 중복 임계치 종료
- 키워드별 로그/요약 반영

이 단계가 두 번째인 이유:
- 가장 빠르게 실행 시간을 줄이고 운영 체감을 개선할 수 있음

### 3단계. 상태/이력

- 스키마 확장
- 감지 로직 추가
- 변경 이력 테스트

이 단계가 세 번째인 이유:
- 스키마 영향이 크고, 앞 단계의 실행 기준이 안정된 뒤 넣는 편이 안전함

### 4단계. 운영성 정리

- 출력/로그 정리
- 수동 도구 이동
- 의존성 청소
- 문서 갱신

## 6. 테스트 전략

### 단위 테스트

- 실제 삽입 여부 반환 테스트
- 중복 URL 처리 테스트
- 회사 상세 대상 dedupe 테스트
- 증분 종료 조건 테스트
- 상태 전이 및 이력 기록 테스트

### 통합 테스트

- 키워드 1개 기준 Phase 1 전체 흐름
- 동일 공고 재수집 시 `last_seen_at` 갱신 확인
- 필드 변경 시 history 생성 확인

### 수동 검증

- 1개 키워드, 낮은 `MAX_PAGES`로 실제 실행
- 로그, 실행 요약, DB 결과 대조

예상되는 주요 수정 대상:

- `main.py`
- `database.py`
- `config.py`
- `crawler.py`
- `tests/test_database.py`
- `scripts/manual_test_crawler.py`
- 신규 마이그레이션/DDL 문서
- 신규 상태/이력 테스트 파일

## 8. 리스크와 대응

### 리스크 1. 스키마 변경으로 기존 데이터 호환성 문제

대응:
- `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 우선
- 기본값과 null 허용 정책을 먼저 적용

### 리스크 2. 증분 종료가 너무 이르게 발생

대응:
- 임계치를 설정값으로 분리
- 로그에 종료 사유와 연속 중복 수 출력
- 초기에는 보수적 기본값 사용

### 리스크 3. 상태 전이 규칙이 과도하게 단순함

대응:
- 첫 버전은 `active/stale` 정도의 최소 모델로 시작
- “closed” 확정은 충분한 관측 규칙 확보 후 확장

## 9. 정의된 완료 조건

- 실행 요약이 실제 DB 반영 결과와 맞는다.
- 동일 회사가 Phase 2에서 중복 방문되지 않는다.
- 연속 중복 기반 조기 종료가 동작한다.
- 공고 상태/이력 최소 구조가 DB에 반영된다.
- 자동 테스트가 추가되고 기존 테스트가 유지된다.
- 수동 도구와 테스트 모듈의 역할이 분리된다.
- 문서가 최종 구현과 다시 동기화된다.

## 10. 다음 액션 제안

이 기획안 기준 첫 구현 배치는 아래 순서가 적절합니다.

1. 데이터 신뢰성 패치
2. 증분 크롤링 도입
3. 상태/이력 스키마 추가
4. 운영성 정리와 문서 마감

가장 먼저 시작할 구현 단위는 **`insert_job_posting()` 반환값 정리 + Phase 2 대상 dedupe + 실행 통계 수정** 입니다.
